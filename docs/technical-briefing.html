Mangrove Research — technical briefing for a graph/DB conversation

A cognitive prosthetic for human-AI memory

Draft September 2026. For a colleague with a strong graph and database background. Intended to make a technical conversation productive by establishing what the system is, why it is designed this way, and where the hard questions are.

The problem being solved

Most tools for knowledge and memory are built on hierarchical or linear structures — folders, lists, timelines, tables. These structures are easy to implement and easy to query. They are a poor match for how human cognition actually works, and a particularly poor match for the way neurodivergent (ND) minds — ADHD, autistic, dyslexic — tend to organize and retrieve information.

Human memory is associative and context-dependent. A thought is retrievable not because it sits at a predictable address, but because you can follow a chain of related things to find it. Things belong in multiple places simultaneously. Connections between distant concepts are often the most valuable things — and they are exactly what flat structures lose.

ND brains tend to have a particularly high density of these cross-domain connections. The scatteredness that feels like a problem is often a structural feature: the thinking is richly connected, but the tools impose a flat address space it was never meant to fit in.

The core claim of this project: the right structure for an external cognitive memory is a labelled property hypergraph with a temporal axis — not a folder hierarchy, not a relational database, not a flat document store. The connections are first-class. Chronology is an axis, not a primary key. Multiple things can be simultaneously true, in development, or valid for different contexts.

What the system consists of

The corpus
~15 million words of conversation across two years — Claude AI, Claude Code, ChatGPT, and other tools. Append-only. Contains the actual reasoning behind every decision.
The graph (Epoch)
A multiplex property hypergraph. Same nodes, multiple relationship layers (semantic, provenance, access, temporal). Hyperedges for relationships with more than two participants.
Extraction cascade
Pipeline that reads conversations and produces typed graph nodes and edges. Still being built. Conversations currently produce structured documents as a workaround.
Materialized views
Human-readable outputs from the graph: notebook, wiki, summaries. CQRS-inspired model — write model (graph) and read models (views) separated.
Agent team
Named AI agents with specific roles. Blackboard architecture: agents monitor the graph for relevant work and act. No central controller.
Projection surfaces
Separate repos/apps that read from the graph for specific purposes. All read-only projections. None write back.

Key design decisions

Graph not relational
Relationships are first-class data. A conversation references a project, decision, person, principle, and time interval simultaneously. The graph makes relationships the structure.
Hypergraph not simple graph
Many relationships are not binary. A meeting involves multiple participants. A hyperedge connects any number of nodes. This is the right primitive.
Multiplex layers
Same nodes, distinct edge types: semantic, provenance, access, temporal. Each layer can be queried independently while nodes are shared.
Allen's interval algebra
Timestamps are insufficient. Interval relationships matter (overlaps, during, meets, contains). Same formalism used in the Choreotope movement-notation project.
Append-only corpus
Raw conversation corpus never modified. History of reasoning is itself research data.

The self-similarity

Layer 0
Raw, append-only. Conversations, rough ideas. No commitment to structure.
Layer 1
Typed, named. Graph nodes with identity and type.
Layer 2
Relational. Hyperedges — how things relate to each other.
Layer 3
Materialised views. Human-readable projections of the graph.

This appears in the design system, research practice, engineering, and principle hierarchy. The shape is the same in every domain. For ND people, recognising this self-similarity is load-reducing: one mental model, many materials.

Questions for the graph/DB expert

1What graph database fits this model? Needs: hyperedges, multiplex layers, temporal interval properties, property graphs, full-text search. Tradeoffs between Neo4j, ArangoDB, Memgraph, TigerGraph?
2Deduplication in the extraction cascade. Canonical patterns for idempotent event-driven ingestion into a graph?
3Temporal consistency at scale. How to store and query Allen interval relationships efficiently? What indexing strategies exist?
4Hyperedge schema. What shape works for an edge connecting 4+ nodes, with its own properties, participating in multiple layers?
5Community detection and summarisation. Established algorithms for cluster detection in a multiplex hypergraph? Where does LLM summarisation plug in usefully?
6Graph versioning. Snapshot vs. temporal graph (versioning as intrinsic to every node and edge)?
7Access patterns. Neighbourhood traversal, temporal subgraph extraction, cross-layer queries, full-text into Layer 0. What query language and indexing does this imply?
